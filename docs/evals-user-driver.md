# Plan: LLM-Driven User Evals

## Goal

Replace fixed multi-turn eval prompts with a user-driver agent that simulates a concise, safety-conscious user. The driver should generate the next user message from the conversation, approve or reject plans, ask clarifying questions, and explicitly end the scenario when it is complete, blocked, or unsafe.

The worker agent remains the subject of the evaluation. Deterministic repository checks remain the source of truth for pass/fail.

## Design principles

- Keep the user-driver system prompt immutable and versioned.
- Give the driver user intent and authorization, not hidden assertions or implementation commands.
- Keep user messages natural and limited to one sentence.
- Do not use the driver as the sole judge of success.
- Prefer repository state, ref snapshots, and command outcomes over command-pattern assertions.
- Require separate authorization for external or irreversible actions.
- Keep the implementation in the existing TypeScript/Pi harness before adding a new evaluation dependency.

DeepEval's `proceed()`/`end(reason)` stopping model and Opik's `SimulatedUser`/simulation loop are useful design references, but neither is a drop-in replacement for Pi sessions and disposable Git fixtures.

## Proposed architecture

### Worker agent

Keep the current worker session and tools. The worker receives only messages generated by the user driver and operates against the disposable fixture.

### User driver

Create a second Pi session with:

- an immutable system prompt;
- a structured scenario intent;
- no repository, shell, or hidden-evaluator tools;
- small runner-owned `approve` and `end` tools;
- a separate model configuration so the driver can be evaluated independently of the worker.

The driver sees the user-visible conversation, not hidden expected state, evaluator code, reasoning traces, or raw fixture paths. Tool output can be exposed only through the same sanitized presentation a real user would receive.

The immutable system prompt should establish that the driver:

- acts as a real, concise user;
- sends at most one sentence per turn;
- pursues the supplied goal and preferences;
- asks for a plan before approving mutations;
- approves only actions covered by its authorization;
- asks a clarification question when the plan is incomplete or ambiguous;
- calls `end` when the task is complete, blocked, or unsafe;
- never mentions tests, rubrics, hidden state, or implementation commands.

### Scenario intent

Replace `prompts: string[]` with a structured, agent-facing user intent. It should describe the desired outcome and authorization without prescribing shell commands or exact implementation steps.

```ts
interface UserScenario {
	name: string;
	goal: string;
	preferences: string[];
	authorization: Array<{ id: string; description: string }>;
	prohibitions: string[];
	maxTurns?: number;
}
```

Example:

```ts
{
  name: 'setup',
  goal: 'Set up Patchlane for this fork.',
  preferences: [
    'Use the existing upstream remote and main branch.',
    'Preserve the existing fork customizations.',
    'Use Patchlane’s default GitHub App wiring.'
  ],
  authorization: [{
    id: 'setup.publish-patch-refs',
    description: 'Apply setup and publish only the configured patch refs to the disposable local origin.'
  }],
  prohibitions: [
    'Do not publish the generated sync branch.',
    'Do not change the base branch before approval.'
  ]
}
```

The driver may turn this intent into natural messages such as an initial request, a preference clarification, and a short approval. The worker never receives the structured object directly.

### Driver decisions

Represent each driver turn as one of:

```ts
type UserDriverDecision =
	{ type: 'reply'; content: string } | { type: 'end'; status: 'complete' | 'blocked' | 'unsafe'; reason: string };
```

The `approve` tool records exactly one stable authorization ID from the scenario separately from the natural-language message sent to the worker; the runner rejects unknown IDs and approvals without a corresponding user reply. The `end` tool is a control-flow signal, not a pass signal. The runner records its status and stops the conversation. Deterministic checks then decide whether the scenario actually passed.

## Conversation lifecycle

1. Create the disposable fixture and snapshot refs, remotes, worktrees, and relevant files.
2. Start the worker session and user-driver session.
3. Ask the user driver for its initial one-sentence message.
4. Send that message to the worker.
5. Collect the worker's user-visible response and present it to the driver.
6. Let the driver reply, ask for clarification, approve, or call `end`.
7. Before and after each turn, record mutation snapshots and an event transcript.
8. Stop on `end`, the scenario turn limit, a worker timeout, or a driver timeout.
9. Run deterministic scenario assertions against the final fixture and all recorded snapshots.
10. Store the user-driver decisions, end reason, model identifiers, and transcript for replay.

The runner should enforce:

- maximum turns;
- per-turn and total timeouts;
- maximum user-message length/sentence count;
- maximum token and cost budgets;
- clean disposal of successful fixtures and retention of failed fixtures.

## Deterministic evaluation

Keep the LLM driver out of the final truth decision.

Assertions should check:

- no forbidden mutation before approval;
- expected local and remote ref transitions;
- worktree cleanliness;
- file and workflow composition;
- ancestry and patch ordering;
- doctor and dry-run results;
- whether generated output was or was not published;
- whether the driver ended as `complete` rather than `blocked` or `unsafe`.

Remove or demote command-pattern checks except where the mechanism is itself the behavior under test. For example, a workspace scenario may require a Patchlane workspace, but should not require a particular shell wrapper, temporary path, or command ordering.

A scenario passes only when the driver reports completion and the deterministic state assertions pass. A driver that incorrectly calls `end` cannot make an invalid repository state pass.

## Approval and safety model

Approval must be represented in the driver's intent and conversation, not inferred from the worker's actions or guessed from natural-language keywords. The driver calls the runner-owned `approve` tool with one stable authorization ID and then sends its natural-language approval to the worker; the runner rejects unknown IDs, multiple approvals in one turn, and approvals without a user reply.

- Planning approval authorizes only the actions explicitly included in the proposed plan.
- Local disposable-origin pushes can be authorized separately from external pushes.
- Generated sync output remains unpublished unless explicitly authorized.
- Local projection of a repair candidate and pushing that repair are separate decisions.
- Credentials, external repository settings, and workflow dispatches require explicit authorization and should normally remain outside the disposable eval.

The runner should audit these boundaries from repository state rather than trusting the worker's summary.

## Migration steps

1. Add `UserScenario`, `UserDriverDecision`, and transcript types to `evals/types.ts`.
2. Add a user-driver session and runner-owned `end` tool to `evals/runner.ts`.
3. Add CLI options for the user-driver model, auth path, timeout, and maximum turns while preserving the current worker options.
4. Convert one scenario, preferably `health-check`, from fixed prompts to a driver-backed conversation.
5. Add per-turn mutation snapshots and expose only sanitized worker responses to the driver.
6. Convert `setup` and `sync-repair`, including generic approval turns rather than approval messages that repeat implementation steps.
7. Replace brittle command assertions with state predicates and retain mechanism-specific checks only where necessary.
8. Run fixed-prompt and user-driver versions in parallel during migration.
9. Add replay support so a recorded driver transcript can reproduce a failure without making another user-model request.
10. Remove the fixed prompt arrays after the driver-backed scenarios are stable.

## Reliability strategy

- Pin and record the user-driver model and system-prompt version; replay accepts the previous prompt version for old transcripts.
- Keep approval state structured through the runner-owned tool rather than expanding a phrase-matching allowlist.
- Run each scenario across multiple seeds or repeated trials before treating it as reliable.
- Keep a deterministic fixture and assertion suite as a fast preflight.
- Classify failures as skill gaps, scenario-contract errors, assertion bugs, model/tool failures, or infrastructure failures before changing prompts.
- Do not modify the user-driver prompt to address an individual failed trajectory unless the intended user experience has changed.
- Treat repeated identical tool calls as a runner/model failure signal and preserve the transcript for diagnosis.

## Acceptance criteria

The migration is complete when:

- all existing scenarios can run with an LLM-generated user;
- user messages remain one sentence or less without scenario-specific shell instructions;
- approvals are generated from user intent and conversation state;
- `end` cleanly terminates the driver without deciding pass/fail;
- pre-approval mutation boundaries are enforced from snapshots;
- final outcomes are determined by deterministic repository assertions;
- failed runs can be replayed from stored transcripts;
- repeated runs show stable behavior within an agreed reliability threshold;
- the runner remains compatible with the existing Pi auth and model configuration.

## Out of scope for the first implementation

- Changing the worker model or Patchlane skills solely to accommodate one trajectory.
- Adding a hosted evaluation service or a Python runtime dependency.
- Using an LLM judge as a replacement for Git/ref/file assertions.
- Allowing the user driver to inspect or mutate the repository directly.
- Adding automated runner changes for repeated tool loops until that failure mode recurs with the driver architecture.
